# Flutter with Patrol

Patrol drives a Flutter app and the native platform around it (permission dialogs, airplane mode, other apps) from Dart tests. Native automation only runs under `patrol test` or `patrol develop`, never `flutter test`, and the `patrol` and `patrol_cli` versions must match the compatibility table (a mismatch is the most common user-error cause). LeanCode's suite convention finds widgets only by keys shared with the app, and once the test passes move every Patrol call into feature modules. The canonical docs are the source of truth for versions, native config and code: follow them at each step instead of guessing.

**Contents:** [First-time setup](#first-time-setup) · [Running and Patrol MCP](#running-and-patrol-mcp) · [Order of work for a new test](#order-of-work-for-a-new-test) · [Suite architecture](#suite-architecture) · [API, actions and assertions](#api-actions-and-assertions) · [Native dialogs](#native-dialogs) · [Test keys](#test-keys) · [When a run fails](#when-a-run-fails) · [Prove it](#prove-it)

## First-time setup

The first setup covers Android only: the pubspec `patrol:` block plus native Android. Tell the user up front. iOS and other platforms follow the same install doc but are not part of it.

1. **Configure:** add the `patrol` dev dependency and the `patrol:` block in `pubspec.yaml` ([dependency](https://patrol.leancode.co/documentation#add-patrol-dependency)); then native Android: the test runner, the orchestrator and `MainActivityTest.java` ([Android setup](https://patrol.leancode.co/documentation#android-setup); [Groovy build files](https://patrol.leancode.co/documentation#old-android-setup)); then build flavors if the project uses them ([flavors](https://patrol.leancode.co/documentation#flavors)).
2. **Write a first minimal, self-contained test:** only Flutter framework widgets, no app or backend dependencies, so a green run proves the harness itself. Put it in `patrol_test/` (or the configured `test_directory`). See [write your first test](https://patrol.leancode.co/documentation/write-your-first-test).
3. **Gitignore** `test_bundle.dart` (generated by Patrol) and `.patrol.env` (your dart-defines, often secrets) ([setup](https://patrol.leancode.co/documentation#setup)).
4. **Boot an Android emulator and wait for boot to fully complete;** a test launched mid-boot fails. Then run the single test with `patrol test`. A green run confirms the setup.

- **`MainActivity` cannot be resolved (Java):** set the `package` in `MainActivityTest.java` to the app's `applicationId`.
- **Other errors** (bundle build failures, hangs, flavor mismatches): the [FAQ](https://patrol.leancode.co/documentation#faq).
- **Once setup is green,** mention that Patrol MCP exists and can be set up on request ([patrol_mcp](https://pub.dev/packages/patrol_mcp)). The user decides.

## Running and Patrol MCP

- **Use `patrol test` for tests; when Patrol MCP was selected, its server can run a single test. Never use `flutter test` for Patrol native automation.** [leancodepl/patrol, first-time setup and running]
- **MCP tools:**
  - `patrol-run({ "testFile": "patrol_test/your_test.dart" })` runs a test and waits for it to finish. With no session running it starts one with that file; with a session running it restarts the current tests.
  - `patrol-screenshot({ "platform": "android" })` or `"ios"` captures a screenshot to debug a failure.
  - `patrol-native-tree({})` fetches the current native UI tree, for writing native interactions and for driving apps other than the app under test.
  - `patrol-status({})` shows the status and recent output; `patrol-quit({})` quits the session gracefully.

## Order of work for a new test

The pattern: inline first, prove it green, refactor into reusable units, prove it green again.

1. **Read the key files directly:** the modules aggregator, the test wrapper, the main `keys.dart`, and the app's feature files for the scenario. These are known paths; open them, don't search for them.
2. **Inspect existing modules** for functions to reuse.
3. **Consider whether an existing function can be adjusted** to fit both its current use and the new test.
4. **Assign test keys** to the elements you need, if they don't have keys yet.
5. **Write the test** in a new file, reusing existing modules and functions.
6. **Write Patrol actions directly in the test file.** Don't create new module methods yet.
7. **Run the test often,** after each logical group of steps, to catch failures early.
8. **Once the full test passes, move the new code into existing or new modules.** This is mandatory in the module architecture: the test file may only call module methods, never Patrol APIs directly. (Without that architecture, reorganize the new code into reusable functions.)
9. **Rerun the test** after reorganizing to confirm it still passes.

## Suite architecture

LeanCode's recommended architecture: Modules, System and ApiClients, used through a custom `testApp` wrapper for all tests, with one test per file.

- **Module:** one feature from the user's point of view (Auth, Home screen, Downloads, Player).
- **System:** a class extending `PlatformAutomator` for native interactions through `$.platform` that are not part of your app (enabling airplane mode to test offline). Only methods that fit no app module go here.
- **ApiClients:** one class grouping the API clients a test talks to, one client per API (a test email server, the test backend, third-party services).
- **Method style:** no comments in methods, descriptive names instead. Split a long module method when its length hurts reading and it covers several nameable steps. When a series of steps is reused whole across many tests (a long onboarding), give the module a wrapper method that calls one private method per step.
- **Files:** `patrol_test/modules/home.dart`, `patrol_test/modules/modules.dart` (the aggregator), `patrol_test/modules/system.dart`, `patrol_test/modules/api_clients.dart`.

```dart
// patrol_test/modules/home.dart
import 'package:patrol/patrol.dart';
import 'module.dart';

final class Home extends Module {
  Home(super.$);

  Future<void> navigateToSettings() async {
    await $(keys.home.settingsButton).scrollTo().tap();
  }

  Future<void> searchForItem(String searchPhrase) async {
    await $(keys.home.searchButton).scrollTo().tap();
    await $(keys.home.searchInput).enterText(searchPhrase);
    await $(keys.home.searchSubmitButton).tap();
  }
}
```

```dart
// patrol_test/modules/modules.dart
final class Modules {
  Modules(this._$);
  final PatrolIntegrationTester _$;

  late final home = Home(_$);
  late final auth = Auth(_$);
}
```

```dart
// patrol_test/modules/system.dart
final class System extends PlatformAutomator {
  System({required super.config});

  Future<void> checkIfNativePlayerIsVisible() async {
    // Implementation
  }
}
```

```dart
// patrol_test/modules/api_clients.dart
final class ApiClients {
  final backend = BackendClient();
  final mailpitClient = MailpitClient();
}
```

A test then reads as module calls (abridged; the `testApp` callback is `($, modules, system, apiClients)`):

```dart
testApp('Download a chapter and play it offline', ($, modules, system, apiClients) async {
    await modules.auth.getAuthToken();
    await apiClients.backend.addFavourites();
    await openApp($);
    await modules.home.goToOldTestament();
    ...
    await modules.player.waitUntilDownloaded();
    // usage of a method from $.platform Equivalent of await $.platform.mobile.enableAirplaneMode();
    await system.enableAirplaneMode();
    ...
    await modules.player.playCurrentTrack();
    // usage of our method, which calls many methods from $.platform
    await system.checkIfNativePlayerIsVisible();
  });
```

## API, actions and assertions

- **Any file that uses Patrol APIs directly** (`$()`, `.scrollTo()`, `.tap()`, `.enterText()`, `.waitUntilVisible()`, ...) imports `package:patrol/patrol.dart`.
- **Confirm the API before using it:** search the codebase for existing usage, check the `$.platform` APIs for that action, fall back to https://patrol.leancode.co/, and implement only once the right method is confirmed.
- **Use Patrol's runner for native automation.** `flutter_test` remains usable for assertions and Flutter finders; official Patrol examples import it. The source's package-wide ban confused importing Flutter testing utilities with invoking `flutter test`. Keep the source convention of not writing `patrolSetUp` or `patrolTearDown` manually. [Patrol documentation](https://patrol.leancode.co/documentation), [official package examples](https://github.com/leancodepl/patrol/blob/master/packages/patrol/README.md)
- **No waits around actions:** no `$.pump`, `waitUntilVisible`, `waitUntilExists` or other waits before or after `tap`, `scrollTo` and `enterText`. Patrol waits automatically. Waits belong only at the end of the test.
- **LeanCode suite convention: find widgets only by keys.** This is a source style rule, not an API restriction; official Patrol examples also use Flutter finders. [leancodepl/patrol, patrol-write-test/SKILL.md; https://github.com/leancodepl/patrol/blob/master/packages/patrol/README.md]
- **No try/catch blocks** unless absolutely necessary.
- **LeanCode source convention:** assert at the end and prefer `waitUntilVisible` when sufficient. This is its suite style, not a Patrol restriction. The repository's journey contract keeps actions and specific observable assertions as separate steps where intermediate outcomes matter. [leancodepl/patrol, patrol-write-test/SKILL.md; owner AGENTS.md]
- **After writing a test, run it and fix it if it fails.** When an element wasn't found, check in the app code whether it needs scrolling into view, and adjust the test.

## Native dialogs

- **Handle every native dialog right after the action that triggers it.**
- **For native permissions, prefer `$.platform.mobile.grantPermissionWhenInUse`** over `$.platform.mobile.tap`.

## Test keys

Keys live in a keys file shared between the app and the tests.

- **Key only widgets involved in testing.** Only add the `key` parameter to existing widgets: never change widget signatures, refactor existing code structure, or create new widgets in the app.
- **Never hardcode keys in the app;** use the shared keys file. Never create a key that isn't assigned to a widget. Every key value is unique. Sort keys alphabetically. Add the key as the first constructor parameter.
- **Assign with the exact pattern** `key: keys.feature.widgetName` (unless parameterized). Steps: identify the widget; write `key: keys.feature.widgetName`; define the key in `keys.dart`; verify it is assigned to the widget.

| Use individual keys when | Use parameterized keys when |
|---|---|
| widgets are hardcoded and known at compile time | widgets come from dynamic data |
| widgets have distinct, meaningful names | widgets come from a DTO or enums |
| | the number of widgets is variable or large |
| | widgets are built in loops or from lists |

- **Parameterized keys:** prefer existing enums or DTOs as the parameter, or existing widget properties; when widgets are generated from enums or DTOs, always parameterize with those values. Never assign a parameterized key in the app and use fixed values for it in the keys file, or the reverse. Never create helper methods; use parameterized keys instead.

```dart
// app widget
_Button(
  key: keys.pickSize.sizeButton(size),
  value: size,
  ...
)
// keys.dart
_PickSizeKey sizeButton(SizeDTO size) => _PickSizeKey('sizeButton_${size.name}');
```

- **File layout:** a `keys.dart` next to the feature or widget it belongs to, not in the main lib directory, at most one per feature directory (it may hold several classes): `lib/features/home/keys.dart`, `lib/features/profile/keys.dart`, `lib/features/auth/keys.dart`, `lib/common/widgets/keys.dart`. The main `Keys` class in `lib/keys.dart` only imports and aggregates them; update it when adding a feature keys file.
- **Group related keys in a class named after the screen** (`HomeKeys`), with a private subclass of `ValueKey<String>` that prefixes every value with the page or widget name. Several screens in one file get one prefix class and one keys class each (`_ProductPageKey` with `'productPage_$value'` and `ProductPageKeys`; `_ProductConnectingPageKey` with `'productConnectingPage_$value'`), each keeping its fields alphabetical.

```dart
// lib/features/home/keys.dart
import 'package:flutter/widgets.dart';

class _HomeKey extends ValueKey<String> {
  const _HomeKey(String value) : super('home_$value');
}
class HomeKeys {
  final menuIconButton = const _HomeKey('menuIconButton');
  _HomeKey navbarItem(String label) => _HomeKey('navbarItem_$label');
}
```

```dart
// lib/keys.dart
import 'common/widgets/keys.dart';
import 'features/home/keys.dart';
import 'features/profile/keys.dart';

final keys = Keys();

class Keys {
   final home = HomeKeys();
   final profile = ProfileKeys();
   final widgets = WidgetKeys();
}
```

- **Common widgets** get a `WidgetKeys` class in the directory where the common widget is defined, mixing fixed and parameterized keys (`_WidgetKey` with prefix `'widget_$value'`; `addButton`, `assetRow(String coinTitle)`, `assetSlider(SelectAssetType type)`).
- **Widgets in a separate package** (a widgetbook): that package gets its own `keys.dart` with a `WidgetKeys` class, assigned as `widgetKeys.tile`; `lib/keys.dart` adds `final widgetKeys = ds.widgetKeys;` with `import 'package:common_ui/widgets/keys.dart' as ds;`.

## When a run fails

| Symptom | Likely cause and fix |
|---|---|
| `NativeAutomatorClientException`, "Connection refused … /initialize", native steps not working | the `patrol` and `patrol_cli` versions violate the [compatibility table](https://patrol.leancode.co/documentation/compatibility-table); check them and `patrol doctor` |
| Hangs or errors at load, native never initializes | ran `flutter test`; native automation only runs under `patrol test` or `patrol develop` |
| `:app:connectedDebugAndroidTest FAILED`, "Starting 0 tests", "Process crashed" | Inspect device logs, runner/activity configuration and the installed Patrol/CLI compatibility before attributing the failure. The source's API 35/36 failures were historical symptoms, not a current blanket platform limit. Do not purge global Gradle caches or rebuild as an automatic remedy. [Compatibility](https://patrol.leancode.co/documentation/compatibility-table) |
| iOS `xcodebuild exited with code 65` (or 70) | Inspect the actual signing or build-phase error. The source prescribed deleting the Flutter SDK cache and rebuilding; make any cleanup cause-specific and authorized instead |
| App or data not removed between runs | Check the configured app identity and platform isolation settings. iOS Simulator supports experimental full isolation with `--full-isolation`; the old line said iOS had no API to delete the app between runs. Android supports the documented `clearPackageData` runner setting. [Patrol advanced native usage](https://patrol.leancode.co/documentation/native/advanced) |
| First test passes, the rest fail; stack trace in app packages (`get_it`, DI, `main()`) | app state or singletons aren't reset between relaunches: an app bug |
| Fails only on one physical device or OEM skin | device-specific; retry on the newest `patrol` and `patrol_cli` |
| CI `Java heap space`, or the CLI never terminates on a device farm | `org.gradle.jvmargs=-Xmx8G` (or `JAVA_TOOL_OPTIONS: -Xmx5g` on Codemagic); run `flutter build apk --config-only` before the patrol step; update `patrol` and `patrol_cli`. Device farms are easier than raw CI machines |
| iOS "Could not launch RunnerUITests", `-10661`, runs on macOS instead of the simulator | a non-latest simulator or Xcode 15 with duplicate destinations; pin the OS with `--ios <version>` |
| `scrollTo` throws "no visible (hit-testable) widgets" | by design (hit-testable counts as visible); use `$.scrollUntilExists`, or skip the hit-testable check for non-hit-testable widgets |
| `enterText()` works in the first field but not a focused or autofocus one | a fixed regression; check the `patrol_finders` version |
| `at(0)`, `first` or `last` picks an invisible widget or doesn't wait | the index applies before hit-testing |
| A `/` or odd character in a test name crashes instrumentation | a forbidden character in the name, especially `/` (duplicate of #1839) |

- **Does plain `flutter run` build and launch?** That separates Patrol from a broken app or toolchain.
- **By design, not bugs:** the app relaunches between tests (isolation is intentional); the app must open once to discover tests, so tests cannot run without installing it; `flutter_driver` is not supported.
- **After a new iOS, Xcode, Android or Flutter major release,** suspect a framework-side break before user error and check whether a fix already shipped. iOS Settings-driven native helpers and `-destination` handling break first on a new iOS or Xcode major.

## Prove it

For first-time setup, the self-contained test passes with `patrol test` on a fully booted emulator. When adopting LeanCode's module convention, each new test passes once inline and again after extraction, and the test file calls only module methods. Its shared-Keys convention and ignored `test_bundle.dart`/`.patrol.env` remain scoped to that source suite. Report the selected target, convention and actual checks.
