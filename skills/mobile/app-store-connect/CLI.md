# The asc CLI and the App Store Connect API

`asc` is a third-party command-line client for the App Store Connect API (from `rorkai/app-store-connect-cli-skills`, not Apple; facts from it are tagged [rorkai]). It works through the public API with an API key, and reaches parts the public API lacks (app creation, App Privacy, app groups, some review selections) through a separate Apple Account web session. Before a command, check three things: which auth surface it needs (API key, web session, StoreKit key or Apple Ads), whether you resolved the right IDs before mutating, and whether you ran the dry run before `--confirm`. Builds and signing are in [BUILD-AND-SIGNING.md](BUILD-AND-SIGNING.md); TestFlight, submission and release are in [TESTFLIGHT-AND-RELEASE.md](TESTFLIGHT-AND-RELEASE.md).

## Discovering commands

All of this section is [rorkai].

- **Start from `--help`:** `asc --help`, `asc builds --help`, `asc builds list --help`. Check `--help` for enum values too.
- **`asc search` finds a command when you know the workflow but not the command path:** local and deterministic. `asc search "submit app for review"`, `asc search --output table "upload build"`.
- **`asc schema` shows the bundled endpoint schemas and request and query fields** before you design API-facing commands: `asc schema --pretty "GET /v1/apps"`, `asc schema --method POST appStoreVersions`.
- **`asc capabilities` explains CLI-supported, partial, web-session and public-API-limited workflow coverage:** `asc capabilities --area release --output table`, `asc capabilities --status web-session --output table`, `asc capabilities --status not-public-api --output markdown`.
- **Verbs:** prefer `view` over the legacy `get` aliases for reads (`asc apps view --id "APP_ID"`, `asc versions view --version-id "VERSION_ID"`, `asc pricing availability view --app "APP_ID"`). Prefer `edit` for update-only surfaces (`asc pricing availability edit --app "APP_ID" --territory "USA,GBR" --available true`, `asc app-setup availability edit --app "APP_ID" --territory "USA,GBR" --available true`, `asc xcode version edit --build-number "42"`). Keep `set` where the CLI models a higher-level replacement or configuration flow and `--help` still shows `set` as canonical.

## Flags, output and pagination

All of this section is [rorkai].

- **Use explicit long flags** (`--app`, `--output`), and prefer explicit flags in automation. Some newer commands prompt for missing fields when interactive.
- **Command-specific flags go after the leaf subcommand.** Parent groups reject misplaced flags.
- **Destructive operations require `--confirm`.**
- **`--paginate` on list commands** so you don't miss IDs; add `--sort` where available for deterministic results.
- **`--next` URLs are opaque continuations:** don't combine them with new filters, sorting or page-size flags; follow the selected command's help for required selectors.
- **Output is TTY-aware:** `table` in an interactive terminal, minified `json` when piped or non-interactive (CI); an explicit `--output` wins. Use explicit `--output json` for automation. `--output table|markdown` is for humans only. `--pretty` is valid only with JSON.
- **Check the exit status, not only stdout.** A failed batch can emit partial receipts: inspect the completed actions and resource IDs before retrying a mutation.
- **In automation wrappers keep data on stdout and diagnostics on stderr.**
- **Timeouts:** `ASC_TIMEOUT` or `ASC_TIMEOUT_SECONDS` for requests, `ASC_UPLOAD_TIMEOUT` or `ASC_UPLOAD_TIMEOUT_SECONDS` for uploads (for example `ASC_UPLOAD_TIMEOUT=5m`).

## App Store Connect API keys (Apple)

- **Access first:** the Account Holder requests API access under Users and Access > Integrations > Request Access; Apple reviews it case by case.
- **Team keys** (generated by the Account Holder or an Admin) work across all apps and are role-based; "app access can't be limited for an API key". A key's name and access can't be edited after generation.
- **Individual keys:** any user role can generate one by default (Edit Profile > Individual API Key) unless the permission is revoked; one active key per user. Remove the "Generate Individual API Keys" permission to block a user. Individual keys "aren't able to use Provisioning endpoints, access Sales and Finance, or `notaryTool`."
- **The private key downloads once:** "API keys are private and can only be downloaded once." "Apple doesn't keep a copy of the private key." Revoked keys can't be reinstated; keys revoked in the past 30 days show under Revoked.
- **Never commit or ship a key:** "Don't share your keys, store keys in a code repository, or include keys in client-side code." Keys are unique to the App Store Connect API.

### Signing the JWT (Apple)

- **Header:** `alg` = `ES256` ("All JWTs for App Store Connect API must be signed with ES256 encryption"), `kid` = the key ID (for example `2X9R4HXF34`), `typ` = `JWT`.
- **Team key payload:** `iss` = issuer ID (Users and Access > Integrations), `iat`, `exp`, `aud` = `appstoreconnect-v1`, optional `scope`. **Individual key payload:** `sub` = `user` instead of `iss`.

```
{
    "iss": "57246542-96fe-1a63-e053-0824d011072a",
    "iat": 1528407600,
    "exp": 1528408800,
    "aud": "appstoreconnect-v1",
    "scope": [
        "GET /v1/apps?filter[platform]=IOS"
    ]
}
```

- **Lifetime:** tokens with a lifetime over 20 minutes are rejected for most requests. Two minutes suits a one-off request. Long-lived tokens (up to six months) work only when scoped, GET-only, and for these resources: Build Actions, Build Runs, Git References, Issues, macOS Versions, Products, Providers, Power and Performance Metrics and Logs, Pull Requests, Repositories, Test Results, Workflows, Xcode Versions. `scope` ignores `limit`, `cursor` and `sort`.
- **Reuse the token:** "reuse the same signed token for multiple requests until it expires."
- **Call:**

```
curl -v -H 'Authorization: Bearer [signed token]' "https://api.appstoreconnect.apple.com/v1/apps"
```

- **The same JWTs authenticate binary uploads** with the Transporter command-line tool.
- **The XML feed is gone:** IAP, subscriptions, metadata and pricing ended November 9, 2022; Game Center management ended July 15, 2024. Use the REST API.

## Authenticating asc

All of this section is [rorkai].

- **Prefer keychain auth:** `asc auth login`. Fallback env vars: `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_PRIVATE_KEY_PATH`, `ASC_PRIVATE_KEY`, `ASC_PRIVATE_KEY_B64`. `ASC_APP_ID` sets a default app ID.
- **`ASC_BYPASS_KEYCHAIN=1`** is only for repository tests and isolated verification, not normal user sessions.
- **A profile name is a local label,** not an app-level permission boundary.
- **When permissions are unclear, inspect the key's exact role coverage:** `asc web auth capabilities` (a web-session surface; it resolves the current local auth by default, or inspects a specific key with `--key-id`).
- **Create a team API key from a cached web session:** `asc web api-keys create --name "CI uploads" --role APP_MANAGER --output-dir "./keys" --output json`. It needs an Account Holder or Admin session (`asc web auth login --apple-id "user@example.com"`) and saves the one-time P8 as `AuthKey_<KEY_ID>.p8` without printing its contents; choose an explicit private directory with `--output-dir`.
- **StoreKit reads use their own keys:** App Store Server API reads (transactions, subscription status, refunds, notification history) live under `asc storekit` and use separate In-App Purchase keys registered with `asc storekit auth login`, not `asc auth` profiles.

### Web sessions (`asc web auth`)

All of this section is [rorkai].

- **API-key auth (`asc auth`) and Apple Account web sessions (`asc web auth`) are separate.** Prefer the existing keychain API profile for supported operations; inspect `asc auth status` and the command's capabilities before starting a web login.
- **Reuse a cached session:** for web-only work check `asc web auth status --apple-id "user@example.com" --output json` first, reuse an authenticated cached session, and verify its provider matches the intended account before mutations. Don't log out or clear trust or session state as routine preparation.
- **One process owns an interactive sign-in.** While a code prompt is pending, continue that process; coordinate or serialize other agents rather than starting another login that may invalidate the challenge.
- **2FA codes:** trusted-device notification codes and SMS fallback codes belong to different steps; once the CLI announces phone delivery, use the newly delivered phone code, not the earlier notification code. Don't submit bad codes as a resend strategy; inspect the installed command's help for supported recovery.
- **On failure, tell code rejection apart from a timeout** after verification or provider selection. Inspect the exact error and installed version before requesting more codes. A longer request timeout does not prove an interactive-session problem is fixed.
- **After login, verify** `authenticated` and the selected provider with a separate status read, and confirm the next web operation reuses the cache before reporting success. Apple may expire sessions: don't promise permanent unattended auth.
- **Non-interactive fresh sign-in** requires `--two-factor-code-command` or `ASC_WEB_2FA_CODE_COMMAND`; without one it fails before sending the password. Cached-session reuse doesn't need a fresh sign-in. Inspect `asc web auth login --help` before configuring `--two-factor-code-command`. Keep credentials and codes out of logs, source, shell history and PRs. Don't assume a password-manager passkey can be supplied to the CLI or that browser sign-in refreshes its cache; use only mechanisms the installed CLI explicitly supports.
- **Team selection:** `--public-provider-id` takes a public team ID; `--provider-id` takes Apple's numeric provider ID. Never substitute an API profile name for either.

## Resolving IDs

All of this section is [rorkai]. Map human-friendly names to the IDs other commands need.

| ID | Command |
|---|---|
| App | `asc apps list --bundle-id "com.example.app"`, `asc apps list --name "My App"`, `asc apps list --paginate`; default via `ASC_APP_ID` |
| Build | `asc builds info --app "APP_ID" --latest --version "1.2.3" --platform IOS`; recent: `asc builds list --app "APP_ID" --sort -uploadedDate --limit 5` |
| Version | `asc versions list --app "APP_ID" --paginate` |
| TestFlight groups, testers | `asc testflight groups list --app "APP_ID" --paginate`, `asc testflight testers list --app "APP_ID" --paginate` |
| Pre-release versions | `asc testflight pre-release list --app "APP_ID" --platform IOS --paginate` |
| Review submissions | `asc review submissions list --app "APP_ID" --paginate` |
| IAP and subscription owners | `asc iap list --app "APP_ID"`, `asc subscriptions groups list --app "APP_ID"`, `asc subscriptions list --app "APP_ID"` or `--group-id "GROUP_ID"` (all `--paginate --output json`) |
| Digital-goods versions | `asc iap versions list --iap-id`, `asc subscriptions versions list --subscription-id`, `asc subscriptions groups versions list --group-id` (all `--paginate --output json`) |
| Digital-goods children | `asc iap versions localizations list --version-id`, `asc iap versions image --version-id`, `asc iap versions images list --version-id`, `asc subscriptions versions localizations list --version-id`, `asc subscriptions versions images primary --version-id`, `asc subscriptions versions images list --version-id`, `asc subscriptions groups versions localizations list --version-id` |

- **Skip build lookup:** `asc versions attach-build` and `asc review submit` accept `--app`, `--version` and `--build-number "45"`.
- **API 4.4.1 digital-goods version IDs are distinct** from IAP product, subscription and subscription-group IDs. Resolve the owning resources first, then their versions, then child localization or image IDs from the version subtree.

## Creating the app record

- **Create the record before uploading a build** (Apple). One record serves a multi-platform single purchase; all platforms share the same bundle ID. Watch-only apps are part of the iOS platform.
- **The Account Holder must sign the latest agreement first:** "You can't add an app to your account until the Account Holder signs the latest agreement in the Business section." Required role: Account Holder, App Manager or Admin.
- **Steps (Apple):** Apps > add (+) > New App > select platforms and enter app info (company accounts can set the developer name) > User Access Limited or Full > Create. Status becomes "Prepare for Submission".
- **The fields you can't undo (Apple):** the bundle ID "can't change this property after you upload a build" and "must match the bundle ID you set in the Xcode project". The SKU (letters, numbers, hyphens, periods, underscores; can't start with a hyphen, period or underscore) can't change after adding the app. The Apple ID is auto-generated, used in the App Store URL, not editable.
- **Name:** "at least two characters and no more than 30 characters", one app name per localization. If another developer uses it and you hold the trademark rights, submit a claim. Product page fields are in [METADATA-AND-SCREENSHOTS.md](METADATA-AND-SCREENSHOTS.md).
- **There is no public API for it.** Apple: "Don't use this API to create new apps; instead, create new apps on the App Store Connect website." [rorkai] drives the web UI with a browser automation tool (Playwright, Cursor browser MCP or equivalent) as an opt-in, local-only workaround with the user signed in (or able to complete login and 2FA). The only manual step should be signing in.

### Driving the New App form

All of this section is [rorkai].

- **Inputs:** app name (max 30 characters), bundle ID (must exist in the Apple Developer portal and be unused by another app), SKU, platform (iOS, macOS, tvOS, visionOS), primary language, user access (Full Access or Limited Access).
- **Preflight:** register the bundle ID if not already registered, confirm no app record exists yet, then open `https://appstoreconnect.apple.com/apps`.

  `asc bundle-ids create --identifier "com.example.app" --name "My App" --platform IOS`
  `asc apps list --bundle-id "com.example.app" --output json`
- **Guardrails:** never export or store cookies; visible browser session only; pause for a final confirmation before clicking "Create" (for standalone scripts); never retry Create automatically on failure.
- **The form:** "New App" (blue "+") opens a dropdown menu with "New App" and "New App Bundle"; click the "New App" menu item, not just the button. Platforms are checkboxes (multi-select). Primary Language is a select: pick by label (for example `"English (U.S.)"`). Bundle ID is a `<select>` that shows "Loading..." and is disabled after platform selection; wait until it is enabled and populated, then select by label like `"My App - com.example.app"`. User Access radios are required (Create stays disabled until all required fields are filled and one is chosen) and sit under `<span>` overlays that intercept clicks: `scrollIntoView`, then click the radio ref directly. The forms are Ember.js, so `browser_fill` may not trigger validation; retype at least one field slowly, or clear it and type slowly. The Create button shows "Creating"; success navigates to `/apps/<APP_ID>/...`.
- **On failure:** if a field or button can't be located, stop and ask the user, take a screenshot, report the last known step; the user checks the browser for validation errors. UI selectors can change without notice: prefer role, label and text selectors over CSS.
- **Verify, then finish setup:** `asc apps view --id "APP_ID" --output json --pretty` (or `asc apps list --bundle-id "com.example.app" --output json`); `asc app-setup info set --app "APP_ID" --primary-locale "en-US"`; `asc app-setup categories set --app "APP_ID" --primary GAMES`; `asc pricing availability create --app "APP_ID" --territory "USA,GBR" --available true --available-in-new-territories true`.

### Availability bootstrap

All of this section is [rorkai].

- **`create` comes before `edit`:** `asc pricing availability create` is only for the first availability bootstrap; `edit` is update-only and for later territory changes once a record exists. First confirm there is no record: `asc pricing availability view --app "APP_ID" --output table`.
- **If Apple rejects the public-API bootstrap, availability is not configured.** Use a web session (`asc web auth login --apple-id "EMAIL"`, then `asc web apps availability create --app "APP_ID" --territory "USA,GBR" --available-in-new-territories true`) or set Pricing and Availability in App Store Connect.
- **Don't assume a standard territory list;** ask the user. Prices are in [PRICING-AND-SUBSCRIPTIONS.md](PRICING-AND-SUBSCRIPTIONS.md).

## Workflows: `.asc/workflow.json`

All of this section is [rorkai]. Workflows are repo-local automation files that run trusted shell commands.

- **Commands:** `asc workflow validate`, `asc workflow list [--all]`, `asc workflow run [--dry-run] <name> KEY:VALUE...`, `asc workflow run <name> --resume "<run-id>"` with the run ID from the JSON result. Don't pass extra `KEY:VALUE` params with `--resume`; the saved workflow file, params and persisted outputs are reused. Stdout is machine-readable JSON; step output streams to stderr. Verify flags with `asc workflow --help` and each subcommand's `--help`.
- **File:** default path `.asc/workflow.json`, override with `asc workflow run --file ./path/to/workflow.json <name>`; JSONC comments are supported. Top-level hooks: `before_all`, `after_all`, `error`. Workflow keys: `description`, `private`, `env`, `steps`. Step forms: string shorthand, `run` (shell command), `workflow` (sub-workflow call), `name`, `if` (conditional var name), `with` (env overrides for workflow-call steps), `outputs`, `retry`, `timeout`.
- **Outputs:** `${steps.step_name.OUTPUT_NAME}`, extracted from the step's JSON stdout (so pass `--output json`), for example `"BUILD_ID": "$.data.id"`. A step that declares outputs needs a reference-safe `name`; output-producing names must be unique across workflows that can execute together in the same run graph. Outputs are allowed on `run` steps only. They persist in run state, so never map secrets into them.
- **Retry and timeout:** add retry only to commands you have determined are safe to repeat; the runner doesn't classify commands or retry mutations on its own. `retry.max_attempts` is 2 to 100 and counts the first attempt; delays and timeouts are positive and at most 24 hours; both work only on `run` steps, not workflow calls or lifecycle hooks. A timeout without retry is terminal because the command may have completed remotely; pairing retry and timeout is the signal that another attempt is safe. Resume needs a successful checkpoint or a retry-enabled failed step; output-extraction failures can't be resumed.

```json
{
  "name": "resolve_build",
  "run": "asc builds info --app $APP_ID --latest --platform IOS --output json",
  "retry": {
    "max_attempts": 3,
    "delay": "5s"
  },
  "timeout": "2m"
}
```

- **Params:** `KEY:VALUE` or `KEY=VALUE`, repeated keys are last-write-wins, referenced through shell expansion as `$VERSION`. Env precedence: `definition.env < workflow.env < CLI params`; for a sub-workflow call with `with`, `sub-workflow env < caller env and params < step with`. `"if": "VAR_NAME"` is truthy for `1`, `true`, `yes`, `y`, `on` (case-insensitive); lookup checks merged workflow env and params first, then the process environment.
- **Example workflow:**

```json
{
  "env": {
    "APP_ID": "123456789",
    "VERSION": "1.0.0",
    "GROUP_ID": ""
  },
  "before_all": "asc auth status",
  "after_all": "echo workflow_done",
  "error": "echo workflow_failed",
  "workflows": {
    "beta": {
      "description": "Resolve the latest build and distribute it to TestFlight",
      "steps": [
        {
          "name": "resolve_build",
          "run": "asc builds info --app $APP_ID --latest --platform IOS --output json",
          "outputs": {
            "BUILD_ID": "$.data.id"
          }
        },
        {
          "name": "list_groups",
          "run": "asc testflight groups list --app $APP_ID --limit 20 --output json"
        },
        {
          "name": "add_build_to_group",
          "if": "GROUP_ID",
          "run": "asc builds add-groups --build-id ${steps.resolve_build.BUILD_ID} --group $GROUP_ID"
        }
      ]
    },
    "release": {
      "description": "Validate, stage, and submit an App Store version",
      "steps": [
        {
          "name": "validate",
          "run": "asc validate --app $APP_ID --version $VERSION --platform IOS --output json"
        },
        {
          "name": "stage",
          "run": "asc release stage --app $APP_ID --version $VERSION --build-id $BUILD_ID --metadata-dir ./metadata --confirm --output json"
        },
        {
          "name": "submit",
          "if": "SUBMIT_FOR_REVIEW",
          "run": "asc review submit --app $APP_ID --version $VERSION --build-id $BUILD_ID --confirm --output json"
        }
      ]
    },
    "publish-appstore": {
      "description": "High-level upload plus App Store review submission",
      "steps": [
        {
          "name": "publish",
          "run": "asc publish appstore --app $APP_ID --ipa ./build/MyApp.ipa --version $VERSION --wait --submit --confirm --output json"
        }
      ]
    }
  }
}
```

- **Useful invocations:**

```bash
asc workflow validate | jq -e '.valid == true'
asc workflow list --all --pretty
asc workflow run --dry-run beta BUILD_ID:123 GROUP_ID:grp_abc
asc workflow run beta BUILD_ID:123 GROUP_ID:grp_abc | jq -e '.status == "ok"'
asc workflow run release BUILD_ID:123 SUBMIT_FOR_REVIEW:true
asc workflow run release --resume "release-20260312T120000Z-deadbeef"
```

- **Safety:** treat `.asc/workflow.json` like code: run trusted, version-controlled files only, never from untrusted PRs with secrets. Validate, then dry-run, then run. Use explicit IDs and `--confirm` for mutating steps, and the current commands (`asc validate`, `asc release stage`, `asc review submit`, `asc publish appstore`), not removed submission commands.

## Removed and deprecated

All of this section is [rorkai].

- **Removed in 5.0.0:** `asc signing sync --password`, `asc subscriptions review submit`, `asc iap submit`.
- **Removed shortcuts (no version given):** `submit-preflight`, `submit-create`, `release-run`.
- **Deprecated:** `--age-rating-override` (use `--age-rating-override-v2`), Apple Ads Campaign Management API v5, Xcode's `ad-hoc` export method.

## Prove it

- `asc auth status` shows the expected profile, and a separate `asc web auth status --apple-id "..." --output json` shows `authenticated` and the intended provider before any web-session mutation.
- `asc apps list --bundle-id "com.example.app" --output json` returns exactly one app, and `asc apps view --id "APP_ID" --output json --pretty` matches it.
- Every list used to resolve an ID ran with `--paginate`, and every mutation exited 0 with the resource IDs captured.
- `asc pricing availability view --app "APP_ID" --output table` shows a record after the bootstrap.
- `asc workflow validate` passes and `asc workflow run --dry-run <name>` shows the intended steps before the real run.
- No `.p8` key appears in the repository, client code or logs.
