# Results and conversations

## Tool results as the product's own components

- **Reuse the product's components,** not a chat-only rendering: the same rows as the list pages, the same cards as the board, the same items as the inbox. The user recognises them and can act on them in place.
- **Read them live from the app's state:** changing a task's status or priority in the chat changes the real task, the title opens its editor, a task the agent created appears once the tasks reload after the answer, and one it deleted is left out. Ids missing from the live list are skipped silently.
- **The stored message keeps ids only.** The full records travel beside the answer as a transient data part, so the cards render at once; a stored chat opened later reads them by id.
- **Don't show an item twice** in one answer, across tools too: a later step that returns items an earlier step already showed (a detail read after a search) renders only the new ones. An empty result (nothing found, or everything already shown) renders nothing, not an empty card.
- **Cap what one answer shows, per kind,** and apply the cap before fetching so only the shown ids are read; count only the records that exist. A kind with its own page stops at about five with no "+N more" (the rest live on that page); tasks stop at six with a ghost "+N more" that toggles the side panel. A failed load replaces the cards with one destructive `role="alert"` line; a failed save on a card shows inline on that card.
- **Leave out what repeats or misleads:** a third party's own summary line in another language that repeats the fields already shown.
- **Pictures from third parties expire:** check which links expired on the server and fetch fresh ones; key the image by its URL so the new picture replaces the hidden broken one, and hide an image that fails to load. Load them lazily with `referrerPolicy="no-referrer"`.
- **A result row:** a picture, a title that opens the item where it lives (with a small outward arrow), and one meta line of the parts present, deduplicated, joined by an `aria-hidden` dot and ending with the source's name. Each part is a `bdi` with its separator inside it, so lines break between parts, never inside one. A part built from two fields (a label and its score) shows only when both are there. A title built from the record's own fields (street or area plus city for a listing), else its type, else its id; a price of 0 reads "free". A picture keeps the kind's icon underneath (both in one grid cell, the image on top), so a hidden or expired image still shows something. Long text clamps to two lines.
- **Counts read naturally:** singular forms ("one group"), the exact figure over an approximate one in a compact number format, and numbers that roll to their new value as a search fills.
- **After an answer,** invalidate what it changed wherever it shows (lists, settings, boards), by tool family: only the families whose tools ran.
- **Seed the app's cache from the data parts as they arrive** (`onData`), so the cards render without a fetch; keep live progress per tool call in its own map, one for the card's progress and one for the status line's.

## Data parts: shown, stored, or both

| Part | Shown | Stored |
|---|---|---|
| Records sent beside the answer, retry notices, live progress | yes | no (transient) |
| The user context, a gate's note, an attached document's text | no | yes (the model reads them later) |
| Follow-up questions | yes, under the last answer | yes, with the answer |

The page sends only text and files; every trusted part is written by the server. A retry notice records the attempt and how many parts the answer had, so "reconnecting" shows only until the answer gains a part. An attached document's stored text keeps a preview, its length and the document's id, and is null when unreadable (a scanned PDF). The server validates stored messages against the tool list before sending them; the client checks only their shape.

## The request and the session

- **The server holds the conversation,** so each request sends only the newest message, the chat's name and pin (saved with the first message) and the locale. Files go as file parts (data URLs), within the same count and size limits the composer checks.
- **Ids are UUIDs made on the client,** the same ones the database stores. Key the chat session by user and conversation, so switching chats starts a fresh session.
- **Continue by itself** once the last answer is complete and every approval has a response (`sendAutomaticallyWhen`).
- **Keep a stored copy in sync whenever no answer is streaming;** the sidebar, search and download read it.
- **Measure the first reply:** the time from send to the first text or tool part, reported as a timing with a budget.
- **One motion config at the page's root:** `LazyMotion` with the DOM animation features loaded once for the page and `strict`, so components use the lighter `m`, inside `MotionConfig reducedMotion="user"` (under reduced motion they keep their fades and drop the movement).

## The conversation list

- **A new chat reuses an empty active one** instead of piling up blanks, and is stored only with its first message; a rename or pin before that is kept locally until then.
- **Until the stored chats load,** the page shows a fresh new chat, and saves and titles wait until the user is known and the load is done.
- **The title:** the name the user gave it, else a title generated after the first complete answer (not after an error or a stop; one that only said hello tries again after the next answer), else the first user message, else "new chat". A generated title never overwrites a name given meanwhile.
- **The title is generated on the server,** which returns none when the chat already has a name or no subject yet; the client applies it only if the owner is the same and the chat is still unnamed. A failed title is logged and the first message stays the name.
- **Pinned first, then newest by creation time** (not last activity). Deleting the open chat opens a new one; deleting every chat (from settings) resets the list to one new chat.
- **Restore once per owner:** opening the app loads the stored chats a single time (an in-flight load kept per owner, so two mounts share it), first resets to a new chat for the new owner (kept when nothing is stored), ignores a response that lands after the owner changed, shows a failed load as a save error, and opens the newest. Run it from the sidebar, which shows on every page. Make the stored list readable on the server, so the page loader renders it on first paint and a hover on the agent link prefetches it; after that the restored state owns it, and sign-out resets it.
- **The header title:** the name in a `bdi` with a "rename" tooltip below; "new chat" for an unnamed chat, nothing with no conversation. Clicking the name turns it into a field exactly as wide as its text (a hidden copy in the same grid cell sets the width, written as `content: attr(data-value) " "` with `white-space: pre`, hidden and zero-height; the input gets `size={1}`, since its default 20-character width would count), focused with the text selected on the next frame; Enter or leaving saves, Escape or an empty or unchanged name cancels. The name and the menu chevron light up each on its own hover; while the menu is open the chevron's fill goes transparent so it doesn't show gray behind the menu. The browser tab reads "<chat name> · <app>" while the chat has messages ("new chat · <app>" or "agent · <app>" until it is named), and gets its old title back on unmount.
- **The chat menu:** pin, rename, download as markdown, delete, behind a chevron labelled "options · <chat name>".
  - **Pin** toggles its label and its icon (pin, unpin).
  - **An item that opens a dialog** closes the menu at once, then the dialog grows out of the trigger; delete counts as one only when the chat has messages.
  - **Rename** uses the same alert dialog as the delete confirm (`alertdialog`, cancel and save in its footer, a hint as its description) and grows out of the menu's trigger and shrinks back into it on close, keyed per opening so it starts from the current name. It is a real `<form>` (Enter saves), its field the initial focus with the text selected, `required` and `autoComplete="off"`, with a live count against the 120-character name limit in rolling digits, and save disabled until the name changed and is not empty. Trim the name and cut it to the limit; the server trims and checks 1 to 120 again, and refuses a change that carries neither a name nor a pin.
  - **Download** writes each message with a body as a `## role` section (localized role names; its text, or its thoughts when it has only thoughts, and a line naming its files by file name, else type), sections joined by blank lines, to a file named by a slug of the title (letters and numbers, dashes trimmed; "conversation.md" when that is empty), through a `text/markdown;charset=utf-8` Blob and a temporary link that is appended, clicked, removed and its URL revoked at once. Disabled for an empty chat.
  - **Delete** removes an empty chat at once; one with messages asks first, naming it and saying the messages cannot be restored.
- **Search on ⌘K or Ctrl+K,** which toggles it (`preventDefault`): an always-open inline combobox with option rows, the first row highlighted and arrows moving the highlight, Enter opening it; a visually hidden title and a backdrop. Empty, it offers "new chat", the pinned chats under a heading, then the rest by date (today, yesterday, the last 7 and 30 days counted from local midnight, then one group per month named by the month alone, so the same month of different years shares one group; all from each chat's creation time); empty groups hide. Typing matches names and message text as a lowercase substring, in one group with no heading; each opening starts empty. Each row shows an icon, the name in a `bdi` and how long ago, and the open chat carries an outline "current" badge; no match gets its own empty state. Opening a chat, or a new one, also goes to the agent page. Keep its open state in a global store: the sidebar that opens it unmounts on phones. Opened from a button it grows out of it (the content wrapped in one child so the morph can counter-scale it, and only the morph moves it); from the keyboard it just fades. The clear button puts focus back in the field.
- **The two shortcuts read the key differently:** search reads `event.code` (`"KeyK"`) with Meta or Ctrl and not with Alt or Shift held, so it works on any keyboard layout; the side panel reads `event.key` lowercased (`"j"`) with Meta or Ctrl, whatever else is held. Both call `preventDefault`.
- **Every write checks the owner** before applying a result, so a read that ends after a sign-out never writes into another user's chats.
- **The sidebar's chats** are a collapsible section: its chevron turns and the list grows in; it follows the page (open on the agent page) until the user toggles it (a state left undefined until then), its list has `aria-controls` and is `inert` while closed, and collapsed to icons the row goes straight to the agent page without `aria-expanded`. The parent row is highlighted only while its list is closed; open, the active chat carries it. "New chat" and "search chats" (with `aria-keyshortcuts="Meta+K Control+K"`, its content in one child so the dialog can grow from it) come first, then the groups (pinned, then recent), each a `section` labelled by its `h3` heading, empty ones hidden.
- **Chat rows are buttons, not links:** the open chat lives in the store, not the URL, and a router marks every link to the current page as current, which lit up every chat at once. Put `aria-current="page"` only on the open chat, and only on the agent page. Each row has a "more" button labelled "options for <title>" at its end that shows on hover, on focus and while its menu is open. On phones picking a row, new chat or search closes the sidebar.

## A side panel beside the chat

A related list (the user's tasks) as a second sidebar: on desktop it pushes the chat aside as it opens (its width slides; content keeps its full width at the outer edge, so it slides in from there), its edge can be dragged wider or narrower within bounds and a click on the edge closes it; on phones it is a bottom drawer you can swipe down over a blurred backdrop. A keyboard shortcut (⌘J or Ctrl+J) toggles it from a ghost icon button with `aria-controls`, labelled with the list's name, and tooltips name the shortcut. Its open state is remembered per browser, with the server render and first client render closed until hydration.

- **It reuses the list page's component** with that page's stored filters (hidden statuses, query, priority, status, created date), sort and whether reordering is allowed, not its board or list choice. Creating an item and its editors open inside the panel. The panel is an `aside` with a label, a `data-open` flag, and a clip layer that inherits the rounded corner around its content.
- **The resize rail:** pointer capture while dragging, ended by `pointerup` or `pointercancel`; a `data-resizing` flag turns off the width transition; the width is a CSS variable clamped between 320 and 720px, the drag delta flipped for right-to-left; a drag of more than 2px swallows the click that would close it. Its label names the click ("close tasks") and its tooltip, toward the chat, the drag ("resize"). The rail is a 16px strip shifted half over the edge, shown only while the panel is open, with a 44px hit area (a `::before` past both sides), a hover line that follows the panel's rounded top corner (an `::after` drawing only its start border with the same corner radius), and no tab stop (the keyboard uses the shortcut).
- **Closed, the panel is `inert`.** On phones the drawer has a handle and a visually hidden title.
