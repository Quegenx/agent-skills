# The composer

## The empty state

- **A greeting by the hour** (morning 5 to 12, afternoon 12 to 17, evening 17 to 22, night otherwise) with the user's first name (from the full name) and the product's mark inline (an `<img alt="">` inside the `h1`), and "how can I help". The server doesn't know the reader's time, so it renders neither greeting nor name (an external-store subscription with a null server snapshot), and the client updates it each minute. Until the account's kind is known, assume the more common one.
- **One composer, two places:** with no messages it sits inside the empty state; once there are messages the same composer is pinned under the conversation.
- **The composer under it, with suggestion chips** for the account's kind (a business and a person get different ones): outline buttons with an icon and a short label, different from the fuller request they insert. A chip **fills the composer** with that request and moves focus and the caret to its end on the next frame; it doesn't send. Chips rise a few pixels from a light blur, one after another. The row wraps and centres inside a horizontal scroller.
- **On narrow screens** the greeting settles at the bottom of the upper half with the composer and chips below it; from tablet width the block centres and the chips move under the composer.

## The cycling placeholder

Over the empty text box only, example requests appear one letter at a time (about 30 ms apart, each fading over 0.3 s), hold for two seconds, then fade out last letter first at a faster pace before the next one. Typing hides it and clears the hold timer; clearing the box starts the current line again from its entry. Keep the phase (enter, hold, exit) in a ref and advance to the next line when the exit completes. Split by graphemes, never inside a letter with its marks, and wrap each word so lines never break inside it (segments `inline-block` with `white-space: pre`, not selectable); `aria-hidden` and `pointer-events: none`. A business and a person get different examples.

## The box

- **A rounded card** with, in order, the queued messages, the attached files as chips, the text box, and a footer with attach (an outline icon button, a gray fill) and dictate (a ghost icon button in the muted color) at the start and send at the end. Buttons inside it keep concentric corners (outer radius minus the padding, computed from the same fluid padding variable). A soft shadow only on wider layouts.
- **The text box grows with its content** (`field-sizing: content`, `rows={1}`) between a minimum and a maximum height, at 16px so phones don't zoom in, its direction taken from what is typed, with an `aria-label`, and it takes focus when the composer opens.
- **Keys:** Enter sends, Shift+Enter starts a new line, nothing happens while an input method is composing; Backspace in the empty box removes the last file.
- **The send button keeps focus in the text** (prevent the mouse-down default) so typing can go on.
- **The text box's attributes:** `enterKeyHint="send"`, spell check off, a `maxLength`, and paste intercepted only when the clipboard holds files (call `preventDefault` only then, so pasting text still works).
- **The footer changes with the state:** while dictating, attach and dictate give way to a ghost "cancel recording" button with a trash icon, and send stays enabled even with an empty box; while the agent answers, send is hidden until something is typed and then reads "queue message", and stop is the primary button when nothing waits to be queued, an outline one when something does. Stop hides while an approval waits, since the card is the way forward.
- **Guard against a double send** while files are being prepared (a ref and a state; the box, attach and dictate disabled meanwhile), so a second Enter doesn't send twice. Clear the draft and the files only once the send or the queueing succeeded.
- **Errors in the composer** (queue full, unreadable files, dictation) show in one line under it with `role="alert"`, one at a time: the file error, else the dictation error. A queue that refuses shows "queue full"; a failed send shows "files unreadable", since reading the files is the only step a send waits for (the message itself is handed to the chat without waiting).
- **Every icon button names itself** in a tooltip, the same name screen readers hear.

## Files

- **Paste or drop anywhere on the composer** to attach; while files are held over it, a dimmed, lightly blurred overlay with an icon, a bold title and a hint says to drop them. React only when the drag's types include `Files`, and always `preventDefault` the drop. A drag that leaves to a child of the form (its `relatedTarget` inside the form) doesn't end it.
- **Decide a document's type by its extension,** lowercased, since browsers name some types differently or not at all, and re-type the upload when the browser's type differs; a name with no dot is refused. Images go by their browser `image/*` type as they are. One map from extension to type (PDF, office files including the macro-enabled and show and template kinds, OpenDocument, RTF, EPUB, CSV, plain text, markdown, images) feeds both the check and the picker's `accept` list. The picker is a hidden `multiple` file input (visually hidden, out of the tab order, `aria-hidden`) that the attach button clicks. Copy the picked files out at once and then reset the input's value, so picking the same file again still fires.
- **Check count, type and size as files are added** and again on the server, with a specific error for each, in that order: a batch that would pass the count is refused whole; then unreadable types are dropped with an error; then files that are too big. Hold one file error at a time (unreadable wins over too big); an add that fits entirely clears it, and so does clearing the files. Nothing is added or removed while files are being prepared.
- **A chip** is a small pill with a tiny thumbnail (or a file icon) and the name; on hover or focus the thumbnail fades out and a remove button fades in on the same spot (labelled and tooltipped "remove <name>", stopping the click from reaching the chip), and a card below previews the image with its name in bold in a `bdi` and its MIME type as code, opening and closing without delay. Each mounted preview holds its own object URL and revokes it on unmount.

## Dictation

- **Stream to a real-time transcription service** over a socket, converting the microphone to 16-bit little-endian mono PCM at the audio context's own sample rate in an audio worklet: clamp to [-1, 1], scale negatives by 0x8000 and positives by 0x7fff, and post chunks of 4,096 samples (about 85 ms) with the buffer transferred. Queue the audio recorded before the socket opens and send it right after the config. Hint the app's language first. Call `resume()` on the audio context yourself, and close it if the worklet fails to load.
- **A single-use key per dictation from your server,** so the service's key never reaches the browser.
- **Stop** releases the microphone at once (its tracks stopped, so the browser's indicator goes off), waits a bounded time for the transcript, and appends the final text plus the still-pending text, trimmed, to the draft; **cancel** throws it away. Stop while still starting is a cancel. Starting clears the last error; a failure while listening cancels and then shows the error.
- **Guard against late starts:** a numbered attempt that was stopped while it waited for the microphone or the key releases what it opened. Leaving the page ends dictation. Name the microphone errors from the `DOMException` name (`NotAllowedError` or `SecurityError`: denied; `NotFoundError`: missing) and report "unsupported" with no secure context or no `AudioWorklet`. A failed key request is a network error.
- **The phases** are idle, starting, listening and finishing. Inline the worklet's code as a Blob URL and revoke it once loaded. Ask the service to identify the language, with the app's language and one other as hints; keep the final tokens and the pending ones apart, and skip the service's control tokens. Finishing waits for the socket to open or close if it has not opened yet, sends an empty frame and waits for the socket to close, up to 10 s, then keeps the final plus the pending text, on a timeout too; an error while finishing only ends the wait. Close the socket in every outcome.
- **Send while dictating** stops first and sends the typed text and the heard text together, joined by a space; on failure the heard text goes back into the draft, after a space unless the draft ends with one.
- **The recording strip** replaces the text: the elapsed time (m:ss, tabular figures, `aria-hidden`, set in state only when the m:ss text changes, not every frame) and a waveform of the microphone level whose new bars appear at the right edge and scroll left, in both directions (the canvas is physical and not mirrored), bars a few pixels wide that fade at both edges, the level sampled every 50 ms and smoothed, with a noise floor and a cap on how much one bar may differ from the last (numbers in [MOTION.md](MOTION.md)). The waveform stays flat until the stream arrives. The whole strip is the stop button: its label names the action ("stop dictation") and its tooltip what follows ("stop and review"). The timer runs before the stream opens; under reduced motion only the timer shows, read live from the media query's `change` event (false on the server); while finishing the timer and waveform hide, it says it is transcribing and the button is disabled. The canvas follows the device pixel ratio and takes its color from CSS (`currentColor`). On cleanup disconnect the source and analyser and close the context.

## Messages sent while the agent works

- **The composer stays usable.** Stop sits beside send; send becomes "queue". What the user sends waits above the text, one muted line each with a remove button, and a hint that it goes when the answer ends and that closing the page drops it.
- **When the answer ends with no approval waiting,** the queued messages go as one message, the trimmed non-empty texts joined by a blank line in order and files together. Sending while an approval card waits would abort the card, so they wait for it too. Only the ones sent leave the queue, and only once the send succeeded (if their files can't be read they stay queued); one queued meanwhile waits for the next answer; a guard stops a double send.
- **Refuse to queue** when the combined message would pass one message's limits (around 5,000 characters, five files, 10 MB each), and keep the draft.
- **Each queued line** previews its text or its file names, and its remove button's label quotes its first 60 characters.
- **The server still refuses a second answer** in the same conversation (a second tab), so the queue is a convenience, not the guard.
