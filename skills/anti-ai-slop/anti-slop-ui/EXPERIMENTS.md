# Recurring interaction experiments

Use Sketchbook's optional batch workflow when the user wants several new interaction ideas over repeated sessions. It differs from [VARIANTS.md](VARIANTS.md), which compares directions for one described UI piece. A kept experiment is a reusable candidate, not automatic permission to replace a production design. [sketchbook, SKILL.md, Counts and the stack are exact; Save the choice; repository owner-design rules]

## Build a new batch from actual choices

[sketchbook, SKILL.md, Read the project; Read the taste file; Generate the batch]

- Read the project's framework, styling, animation library, tokens and fonts first. Build playable interactions in that stack.
- If this recurring workflow has an existing project taste file, read it before choosing ideas. Its Kept and Killed records prevent repeats; its Summary steers the next batch. No file means no demonstrated preferences yet.
- Sketchbook's recipe is six to nine small interactions, with one or two outside the current taste. Those are this batch recipe's counts. The existing three-to-five [variants workflow](VARIANTS.md#phase-3-choose-directions) remains the choice for alternatives to one idea.
- Give each experiment its own interaction idea, a name, a one-line note and Keep and Kill controls in one temporary live gallery. Play every tile before handing it over; a screenshot does not demonstrate its interaction.

## Keep evidence of the user's selection

[sketchbook, SKILL.md, Save the choice; Suggest a clip]

When the user makes a choice in this workflow, update the project taste file in the same turn. The source uses `sketchbook/taste.md`, with Kept, Killed and Summary headings. Record rejection reasons and summarize only what the choices support about easing, speed, density, playfulness and color. A missing reason stays missing; do not invent the user's explanation. This is the selected project workflow's record, not an instruction to write unrelated long-term agent memory.

Move accepted experiments into a clean reusable collection, removing gallery controls from the components. The source uses `sketchbook/kept/`. Delete rejected experimental code after the user's Kill choice, retaining its name and reason. Remove the temporary gallery when the batch is fully sorted and keep it out of production. Preserve unrelated work and any explicit request to retain the exploration surface. [sketchbook, SKILL.md, Save the choice; repository authorization rules]

Name any kept experiments worth a motion clip and explain why. If none were kept, say so. A clip suggestion does not authorize recording, publishing or changing the production UI. [sketchbook, SKILL.md, Suggest a clip; repository authorization rules]

## Prove it

[sketchbook, SKILL.md, The pair; Reporting]

The batch uses the real stack, every played tile is named, previous accepted and rejected ideas were checked, and the records reflect actual user choices. Accepted components remain reusable without gallery chrome; rejected code and the completed gallery were removed within the authorized scope. Identify any tile not played as unverified. Use the repository's P0 to P3 scale rather than the source's HIGH, MEDIUM and LOW labels.
