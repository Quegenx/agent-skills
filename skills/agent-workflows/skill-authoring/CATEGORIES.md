# Skill categories

Cataloging the Claude Code team's internal skills showed they cluster into nine categories. The best skills fit cleanly into one; the ones that try to do too much straddle several and confuse the agent. It isn't a definitive list, but it is a useful framework for finding gaps in your own skills library.

Vercel's [State of agent skills](https://vercel.com/blog/state-of-agent-skills) classified skills.sh skills by the kind of work and by industry. Cross-industry skills are "66% of classified skills and 87.5% of installs", with 3.6 times the installs per listing of industry-specific ones. Agent workflow skills ("how to plan, route work, use tools, and automate browsers") took 14.8% of installs, second to software engineering at 18%, because "a planning skill applies to any job the agent takes on." And "Skills compete within jobs and accumulate across them."

## The nine categories

- **1. Library and API reference:** how to use a library, CLI or SDK correctly, either an internal one or a common one Claude sometimes struggles with. These often include a folder of reference code snippets and a list of gotchas for Claude to avoid when writing a script. Examples: `billing-lib` (your internal billing library: edge cases, footguns, etc.), `internal-platform-cli` (every subcommand of your internal CLI wrapper with examples on when to use them), `sandbox-proxy` (configuring your org's egress gateway for dev work: which hosts are reachable, how to debug "connection refused" errors, how to add an allowlist entry).
- **2. Product verification:** how to test or verify that your code is working, often paired with Playwright, tmux or other external tools. Examples: `signup-flow-driver` (runs through signup → email verify → onboarding in a headless browser, with hooks for asserting state at each step), `checkout-verifier` (drives the checkout UI with Stripe test cards, verifies the invoice actually lands in the right state), `tmux-cli-driver` (for interactive CLI testing where the thing you're verifying needs a TTY).
- **3. Data fetching and analysis:** connect to your data and monitoring stacks. They might include libraries to fetch your data with credentials, specific dashboard IDs, and instructions on common workflows or ways to get data. Examples: `funnel-query` ("which events do I join to see signup → activation → paid" plus the table that actually has the canonical user_id), `cohort-compare` (compare two cohorts' retention or conversion, flag statistically significant deltas, link to the segment definitions), `grafana` (datasource UIDs, cluster names, problem → dashboard lookup table), `datadog` (field reference (@request_id vs trace_id), service list, metric prefix conventions).
- **4. Business process and team automation:** automate a repetitive workflow into one command. Usually fairly simple instructions, but they may depend on other skills or MCPs. Saving previous results in log files helps the model stay consistent and reflect on previous executions. Examples: `standup-post` (aggregates your ticket tracker, GitHub activity, and prior Slack → formatted standup, delta-only), `create-<ticket-system>-ticket` (enforces schema (valid enum values, required fields) plus post-creation workflow (ping reviewer, link in Slack)), `weekly-recap` (merged PRs + closed tickets + deploys → formatted recap post).
- **5. Code scaffolding and templates:** generate framework boilerplate for a specific function in a codebase, possibly combined with scripts that can be composed. Especially useful when the scaffolding has natural-language requirements code alone can't cover. Examples: `new-<framework>-workflow` (scaffolds a new service/workflow/handler with your annotations), `new-migration` (your migration file template plus common gotchas), `create-app` (new internal app with your auth, logging, and deploy config pre-wired).
- **6. Code quality and review:** enforce code quality inside your org and help review code. These can include deterministic scripts or tools for maximum robustness, and can run automatically from hooks or inside a GitHub Action. Examples: `adversarial-review` (spawns a fresh-eyes subagent to critique, implements fixes, iterates until findings degrade to nitpicks), `code-style` (enforces code style, especially styles that Claude does not do well by default), `testing-practices` (instructions on how to write tests and what to test).
- **7. CI/CD and deployment:** fetch, push and deploy code inside your codebase; these may reference other skills to collect data. Examples: `babysit-pr` (monitors a PR → retries flaky CI → resolves merge conflicts → enables auto-merge), `deploy-<service>` (build → smoke test → gradual traffic rollout with error-rate comparison → auto-rollback on regression), `cherry-pick-prod` (isolated worktree → cherry-pick → conflict resolution → PR with template).
- **8. Runbooks:** take a symptom (a Slack thread, an alert, an error signature), walk through a multi-tool investigation and produce a structured report. Examples: `<service>-debugging` (maps symptoms → tools → query patterns for your highest-traffic services), `oncall-runner` (fetches the alert → checks the usual suspects → formats a finding), `log-correlator` (given a request ID, pulls matching logs from every system that might have touched it).
- **9. Infrastructure operations:** routine maintenance and operational procedures, some with destructive actions that benefit from guardrails; they make it easier for engineers to follow best practices in critical operations. Examples: `<resource>-orphans` (finds orphaned pods/volumes → posts to Slack → soak period → user confirms → cascading cleanup), `dependency-management` (your org's dependency approval workflow), `cost-investigation` ("why did our storage/egress bill spike" with the specific buckets and query patterns).

## Verification skills come first

- **They have the most measurable impact:** verification skills have had the most measurable impact on Claude's output quality internally; it can be worth having an engineer spend a week just making them excellent.
- **Make what was tested visible:** have Claude record a video of its output so you can see exactly what it tested, or enforce programmatic assertions on state at each step. Both are often done by including a variety of scripts in the skill.
- **Reviewing before a PR runs on skills too:** before opening a PR, many on the Claude Code team run a few internal skills: one hunts for bugs, one simplifies the diff, and one checks the behaviour end to end. Verification and code review were moved out of Claude Code's system prompt into their own skills it calls selectively.
- **A verification skill takes instructions out of CLAUDE.md:** with several unique instructions on how to verify work, create a verification skill and reference it from CLAUDE.md. To generate one for a project, see [project verification](https://github.com/Quegenx/agent-skills/blob/main/skills/testing/testing/PROJECT-VERIFICATION.md).

## Prove it

The skill names exactly one of the nine categories and holds nothing that belongs to another; a review of the library against the nine lists the categories it lacks; every verification skill ships scripts that assert state at each step or record what was tested.
