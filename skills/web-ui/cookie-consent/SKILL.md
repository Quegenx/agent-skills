# Cookie consent

A consent banner is only the interface: what matters is which code runs before, after and instead of a choice, and whether that holds on a reload, in another tab, after a withdrawal and when the consent backend is down. ## The rules

1. **The banner does not gate anything.** "A banner is only the interface. It does not stop a script you load with a plain `<script>` tag or a vendor SDK you initialize yourself." Register every optional tool with the consent manager and remove its other loaders [c15t].
2. **Assign a category by what the code does.** "Calling analytics `necessary` does not make it necessary." [c15t] ([CATEGORIES-AND-POLICIES.md](CATEGORIES-AND-POLICIES.md#categories-by-purpose))
3. **A permission is not a recorded choice.** Gate code on the permission ("may this run now?"); report and display the recorded choice ("what did the visitor decide?"). "Never turn a permission into a saved choice. Hydrating server state, reading a cookie or rendering a component does not count as a visitor action." [c15t]
4. **Nothing optional runs until the policy has resolved:** "while it loads, and if it fails, every optional category is denied." "A missing banner must never mean 'allowed'." Do not "fix" a missing banner by granting every category or turning consent off [c15t].
5. **Never save a choice on page load** "to make persistence 'stick'. That records consent the visitor did not give." [c15t]
6. **Keep a way back.** "Keep a persistent preferences entry point wherever the policy provides that right. A visitor who dismissed a notice or rejected tracking still needs a way to revisit their choice." [c15t] GDPR Art 7(3): "It shall be as easy to withdraw as to give consent." [https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng]
7. **Withdrawal must stop the tool.** "A one-time gate at startup is not enough." Code that already ran cannot be unloaded, so a revocation reloads the page; gating also leaves cookies behind, so list what each category owns for cleanup [c15t] ([SCRIPT-GATING.md](SCRIPT-GATING.md#withdrawal-stops-the-tool)).
8. **Reject and accept at equal prominence** on a choice prompt; an arm that makes accept primary while reject stays neutral is flagged `equivalent-prominence-overridden` [c15t] ([BANNER-UI.md](BANNER-UI.md#equal-prominence)).
9. **Do not claim compliance.** "Denied consent does not always mean zero network traffic, and choosing c15t does not make the site legally compliant. State the behavior you configured; do not claim compliance." Presets "do not decide which laws apply to your business" [c15t].
10. **Verify by network requests and storage, in a production build.** "'The banner appears' is not a test result." [c15t] ([VERIFY-CONSENT.md](VERIFY-CONSENT.md))

## Prove it

In a production build and a fresh private window, under a policy that asks for a choice: no optional vendor domain appears in the Network panel before a choice (or, for an always-loading Google helper, its consent `default` denies every optional type); Reject survives a reload and a new tab; the footer control reopens preferences with the rejected categories off; allowing one category loads only its vendors, once; turning it off reloads the page, the vendor stays absent and its listed cookies are gone; blocking the init request shows no banner and no vendor request; GPC denies the categories the policy restricts and the restriction ends when GPC is off; the save reaches the backend; and every file's own Prove it checks pass for the parts you touched.
